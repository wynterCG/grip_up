# v0.3: hold-to-grip, arm drag and supported 3D swing

This implements the controls experiment in `../specs/grip_up_controls_v0.3.md`,
with the subsequent user overrides in `../specs/controls_v0.3_user_overrides.md`.
It is separate from v0.2 M3 support-aware posture. No new posture solver,
footwork milestone, level, mantle or reactive challenge is included here.

## Playable configuration

Open `E:\Godot Games\grip_up\project.godot` or launch
`E:\Godot Games\grip_up\builds\GripUp-v0.3.exe`.
The application now starts in **profile 1**, as requested by the user.
The original implementation initially selected the baseline; that caused the
reported W/S arm-extension behavior and has been corrected at startup.

Hold LMB/RMB to keep the corresponding grip. **Move the mouse up to shorten
attached arm targets and down to extend them**, following the user's explicit
inversion request. Both attached arms receive the same requested displacement,
with independent physical-range clamps. Moving the aim toward another hold
continues to affect the supporting arm, including during the other reach.
FREE and REACHING arms never store length input for later attachment.

While gripping, WASD requests camera-relative horizontal 3D swing. W/S never
actuate arm targets in this profile. Grounded, hands-free walking is unchanged.
Mouse-up releases only its own hand immediately. MMB orbit retains grips,
owns mouse motion and discards camera deltas before arm drag resumes.
Space launch is OFF; an explicit comparison checkbox can enable it.

Controls offers the preserved profile 0 (legacy W/S lengths, A/D bias and Space
launch), sensitivity, target-rate adjustment and contact-sound muting. Profile 1
requires hold-to-grip. Predictive catches and physical feet remain separate,
optional experiments and default OFF. The previous `v0.2-M2` tag is preserved.

## Implementation and limits

The input router accumulates raw `screen_relative.y` once for each event and
consumes the total once per physics step. The controller only accepts requests
for the same still-attached anchor, limits the target change to 0.6 m/s and
discards excess, rather than storing a delayed tail. Default sensitivity is
0.0015 m/pixel; deadzone is 0.1 pixel per accumulated step. Changing target
length does not write the body's transform or velocities.

Direction is captured independently for each held WASD gesture. Turning the
camera during a held key does not redirect that gesture; releasing and pressing
again captures the new camera frame. Releasing one of two keys preserves the
other gesture. Ground movement continues using its existing camera reference.

Supported swing is a smoothed, speed-governed grip-reaction torque, using the
existing spring actuators to transmit the resulting motion. It adds no center
of mass force and produces no propulsion without an attached hand. Opposite
torque is applied to dynamic supports, weighted by allocation and engagement.
The same shared limits remain: **360 N hand force, 20 Nm assistance, 150 Nm
combined climbing torque**. A second hand does not double those budgets.
The first attached grip captures the existing twist reference for that support
episode, so camera-only motion does not introduce a twist-control jump.

UI, camera ownership, focus, window boundary and resize transitions clear
pending arm input. Reentry drops the first stale pointer delta. A visible
cursor still has finite screen space; this is not unlimited relative-mouse
capture. Mouse DPI, operating-system motion and ergonomic preferences can
change physical hand travel, so sensitivity remains adjustable.

The hand HUD shows actual and target lengths and load; optional diagnostics
include profile, owner, camera basis, swing request/effective torque and catch
counts. JSONL additionally records arm states, targets, forces, acquisitions,
gesture directions, pointer travel and rebases. Contact/release cues are short
generated prototype sounds with a mute option; their subjective mix is untested.

The physics fixture measures approximately 0.21–0.27 m/s direction-aligned
velocity gain with one hand and 0.13–0.27 m/s with two. In its five-second
phase trial, measured late swing amplitude increases from about 0.09 m passive
to 0.44 m with velocity-timed input. An opposite-input pulse reduces forward
speed to about 0.15 m/s versus 0.39 m/s coasting at 120 Hz. These are controlled
fixture results, not a claim that a human can already reproduce that timing.
Twelve-second continuous input stays bounded and settles rather than building
speed indefinitely. The isolated reaction-pair fixture uses isotropic inertia
to separate actuator conservation from finite-step gyroscopic integration.

Godot MCP Pro invokes `capture_controls.gd` inside the rendered game. Each
frequency completes **16/16 native checks** through held mouse input, including
the inverted sign, W/S target independence, two hands, orbit, hinged support
and the explicit baseline comparison. Reports, screenshots and 20 Hz JSONL
samples are archived in `v03/`. Native timing and screen rays differ from the
headless geometry; matching outcomes, not identical trajectories, are asserted.
No simulated-body pose, velocity, mass or force limit is changed by the capture.

The Windows executable passes a three-frame rendered launch smoke check.
`v03/verification.json` records the executable hash and individual suite totals.
The original Janga grabber's hash is checked unchanged. The licensed MCP plugin
remains local and excluded from the exported game and repository.

## Phase status and remaining human review

v0.3 M0 baseline protection, M1 arm drag, M2 supported swing and M3 interaction
integration are functionally complete. v0.3 **M4 remains open**: a 10–15 minute
human comparison for coordination, repeated transfers, misses, compensation,
fatigue, precision and enjoyment. Automated tests cannot provide those ratings.
The user has requested profile 1 for current playtesting and then reversed its
drag direction; this is not an experimentally established final control choice.

The old route solutions rely on their original controls. Their preservation
does not prove every level is now as easy with the new profile. High-speed or
out-of-reach catches can still fail physically; no aim freeze, free impulse,
infinite strength or automatic retry was added to improve success rates.
